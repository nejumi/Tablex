# AGENTS.md

This repository is building Tablex, a tabular-first prediction meta-harness. Tablex is the current working display name; keep code, package names, API paths, and database tables neutral where practical because the product name may still change.

## Core Rules

- Treat [docs/agent_interface_spec.md](docs/agent_interface_spec.md) as the product contract for Full Auto, Raw, Chat, Research Plan, and marimo behavior.
- Do not read, log, copy, or request secrets.
- Do not pass connector credentials, OAuth tokens, database passwords, or production write credentials to an agent runner.
- Do not pass login passwords, password hashes, session cookies, session-token hashes, Google/OIDC tokens, or user-auth credentials to Codex/AgentRunner workspaces, prompts, artifacts, logs, or reports.
- Kaggle credentials may only be read by harness-owned credential probe/download code in-process; never materialize values into prompts, AgentTaskContracts, runner workspaces, artifacts, or logs.
- Do not include validation or test targets in feature-generation prompts.
- Do not destructively change an approved `evaluation_spec`; create a new version or candidate instead.
- Respect `split_manifest` for all evaluation and baseline work.
- Design important outputs so they can be registered as artifacts with content hashes and lineage.
- Treat `DatasetSnapshot`, `SemanticCatalog`, `Question`, `Assumption`, `Evidence`, `EvaluationCandidate`, `EvaluationSpec`, `SplitManifest`, `ExperimentRun`, `Asset`, `AssetVersion`, `AssetReference`, `LineageEdge`, `Job`, and AgentContextPack artifacts as first-class objects.
- Keep Codex and other runners as implementations of `AgentRunner`; the harness owns UI, auth, metadata, artifacts, lineage, evaluation design, approvals, safety controls, and data access.
- Do not put harness-owned synchronous gates in front of Codex/AgentRunner execution when they can block, delay, or fail before the runner receives the task. Start/control APIs should acknowledge quickly; long-running data science work belongs in a worker/background runner with visible activity and persisted transcript.
- Do not add harness-side "helpful" rules that decide what Codex should be able to infer. Every brittle heuristic, keyword branch, fake workflow gate, or special case placed in front of Codex lowers Tablex quality unless it enforces a real safety, credential, production-write, or evaluation-integrity boundary.
- Codex's path should be stopped only by the user turning the agent power off, by a true hard safety boundary, or by Codex itself explicitly returning a last-resort Give Up state with reasons and required next inputs. Approval prompts in Full Auto are intervention windows, not stops; when the countdown expires, record the assumption and continue.
- Think of Tablex as running alongside Codex: hand over context, skills, data access, evaluation contracts, artifact storage, lineage, and user-facing explanations without stepping into Codex's lane. Do not block the runner's path with convenience workflows, fake readiness gates, brittle heuristics, or ticket-like handoffs.
- When a judgment is needed, delegate it to the main Codex session or an explicit sub-agent with the relevant artifacts. Harness code should avoid judgment logic except for fixed-format validation, artifact registration, lineage, credentials/safety, and EvaluationSpec/SplitManifest consistency checks.
- Treat the harness as a sidecar and workbench around Codex, not a weaker replacement for Codex reasoning. The harness should supply data, artifacts, skills, evaluation constraints, tools, memory, and UI translation; it must not reimplement agent reasoning as brittle fixed workflow logic.
- Treat Full Auto as a continuing autonomous session. The main Codex thread must not be decomposed into many tiny ticket-like Codex jobs. Small queued jobs are acceptable only as child workers for concrete support work such as split generation, model training, notebook rendering, or artifact ingestion.
- If the main agent session returns control, stalls, or waits after child work completes, the harness should re-drive the session with current state and artifacts instead of silently stopping. This heartbeat must preserve Codex autonomy and context rather than replacing it with fixed procedural logic.
- Raw Agent Workspace should preserve the runner transcript as the primary execution record. Harness events may be interleaved as sidecar records, but they must not obscure, replace, or pretend to be Codex output.
- Workflow scaffolding is allowed only as a light, non-blocking guide unless it enforces a real safety, credential, production-write, or evaluation-integrity constraint. It must not create artificial steps where Codex gets stuck before doing useful work.
- Never turn natural-language chat into a keyword-catcher or rule-based ticket router by adding phrase-specific intent branches. This is a prohibited anti-pattern for Tablex.
- Rules, regexes, and deterministic parsers are acceptable for fixed-format inputs such as JSON, schemas, explicit command syntax, file names, metric identifiers, artifact IDs, or structured protocol fields. They must not be used to interpret ordinary human natural-language chat.
- Do not hide, rewrite, replace, or auto-repair Codex-authored human-facing text with harness-side locale, keyword, or quality heuristics. If validation finds a problem, expose factual metadata such as `evidence_verified=false`, schema errors, or missing artifact references, and feed that context back to Codex. Do not mask the authored content unless a real safety, credential, privacy, or legal boundary requires redaction.
- Do not route unrecognized or conversational user messages to `AgentTaskContract` creation by default. A chat turn must first be treated as a human-facing conversation with project context, recent activity, available actions, and uncertainty; create or run tasks only when the agent has a substantive reason to act.
- Do not end Agent Chat with dry ticket issuance such as "AgentTaskContract created" when the user expected an explanation, status update, decision support, or interactive guidance. The agent interface must preserve Codex autonomy and produce a useful human-language response.
- If a natural-language request is ambiguous, let the agent reason from current project state and explain assumptions or proposed actions instead of adding brittle string matching rules.
- This prohibition is not limited to Chat. Avoid ad hoc rules, fake state transitions, placeholder UX, brittle keyword classification, and fixed menu recipes in every product area when they would block Codex/agent reasoning or misrepresent real work.
- Before every code or UI change, run a mental preflight check: am I putting implementer-facing design rationale, architecture vocabulary, self-admonition, fake progress, fixed natural-language analysis, or scaffold prose into a user-facing Chat, Activity, notebook, report, or UI surface? If yes, stop and remove it. Product UI should show what is happening, what changed, what needs attention, and how to continue; it must not expose maker notes such as runner internals, "sidecar", "AgentSession", transcript plumbing, anti-pattern lectures, or explanations of Tablex's design philosophy.
- Do not hard-code human-facing analytical prose to compensate for missing Codex reasoning. Harness-generated summaries may label real artifacts, counts, status, safety boundaries, and provenance, but deeper interpretation, hypotheses, report narrative, notebook story, and user-facing explanations should come from Codex/AgentRunner using project artifacts and equipped Skills, then be stored as artifacts. If Codex has not authored the analysis, label the artifact boundary plainly rather than pretending the scaffold is the analysis.
- Notebook artifacts must not contain harness-authored fixed prose. Do not generate marimo notebook narrative, headings, findings, hypotheses, explanations, or report-like text from backend templates. If a notebook is needed, prepare context/brief artifacts and let Codex/AgentRunner author the notebook, then register that authored output. Harness code may store structured context for the runner, but it must not masquerade as the notebook.
- Native marimo Python source is the notebook artifact of record. Do not use static HTML snapshots as notebook evidence, preview fallback, or a way to hide marimo/runtime failures; surface the failure and let Codex repair or replace the notebook source.
- Harness code may validate and execute schema-checked agent proposals, explicit UI/API commands, artifact IDs, file formats, metrics, and safety policies. It must not pretend those validators are language understanding.
- Research Plan progress must not be inferred from process presence or frontend heuristics. Presence belongs in Activity/turn-state surfaces. Plan structure and current work should come from Codex-authored plan artifacts or a schema-validated ResearchPlan tool substrate; harness verification may add flags and lineage, but must not silently rewrite Codex-authored node status or text.
- Do not infer prediction targets, target-construction semantics, evaluation intent, or modeling intent in harness code through column-name heuristics, keyword matching, or statistical shortcuts. Ask Codex/AgentRunner to reason over the current artifacts and accept only schema-validated proposals back into the harness.
- Prefer evaluation-first changes: data understanding, assumptions, reliable evaluation, and baseline sanity before model optimization.
- Treat baselines as sanity floors and reusable references, not as the product's fixed modeling strategy.
- When proposing modeling approaches, create evidence-backed Ideas and AgentTaskContracts that can use project artifacts, Skill library context, and controlled web/literature research.
- Treat Skills as Codex equipment/context, not fixed recipes or harness-side decision logic. Skills should be cross-project `Asset`/`AssetVersion` records, equipped to projects through `AssetReference`, and materialized into runner context only as guidance, examples, scripts, or reusable craft knowledge.
- Creating or equipping a Skill from chat must go through an explicit UI/API action or a schema-validated agent proposal. Do not implement chat keyword matching such as "if the user says skill then attach X".
- Prepare and inspect AgentContextPack artifacts before real agent execution; they should carry harness-owned evaluation, split, asset, research, and safety context.
- External claims from web or literature research must be returned as Evidence or artifact-backed sources; do not leave them only in runner logs.
- Jobs with external network, production write, or agent execution policy must pass through approval gates before worker execution.
- Reports and visualization specs are first-class outputs and should be registered as artifacts with lineage.
- Keep model prediction enablement separate from local distribution packaging. Every Leaderboard model must preserve its fitted estimator, feature construction, preprocessing, input contract, dependencies, and target-free prediction path well enough to pass isolated smoke validation and run from the UI. Do not require `train.py`, README, or a downloadable local bundle before showing a prediction-enabled model. Build and validate the complete local train/predict bundle on explicit user request from the model menu or for a deliberately selected final handoff candidate, using the registered UI prediction runtime as the canonical inference implementation.
- marimo notebooks are first-class assets. Generated native marimo source notebooks and their structured evidence artifacts must be linked to their DatasetSnapshot, ExperimentRun, ModelVersion, Insight/Idea/Report, and chat context when applicable, so users can open the same in-product marimo viewer from data, model, run, asset, or chat surfaces. Static HTML snapshots are not notebook artifacts or evidence.
- UI work should make complex ML workflow state feel rich, inspectable, and exciting to use; do not collapse product surfaces into plain tracker tables when a focused status gate, preview, or visualization would make the decision clearer.
- Run backend tests and lint/type checks after code changes. Run frontend build or lint when touching frontend code.

## Development Scope

- Initial runtime is single Docker, SQLite, local filesystem artifact store, DuckDB, FastAPI, React, and a Python worker skeleton.
- Do not add W&B, MLflow, Kubernetes, production connectors, Google OIDC, deployment, monitoring, or GenAI feature generation unless the task explicitly asks for that phase.
- Keep implementations understandable and avoid broad abstractions before the MVP vertical slice works.
